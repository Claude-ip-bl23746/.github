<p>排障最浪费时间的方式，是从自己最熟悉的地方开始猜。会改配置的人先查配置，会看网络的人先抓包，结果查了半天发现压根不是那一层。故障树的用处是把「猜」换成「分」：先按症状分成几支，每支只问一个判断问题，答完就往下一层走，走到底自然就是处置动作。</p>
<h2>一、树怎么画：症状在顶，原因在下</h2>
<p>画树的关键是每个分叉只问一个是非题。多问一个，分支就会交叉，走到一半又回到原点。</p>
<h3>顶层只分三类症状</h3>
<p>进不去、进得去但断、进得去也顺但总被拦。这三类对应完全不同的排查路径，先分对类，后面能省一大半时间。分不清的时候看具体表现：卡在登录页属于第一类，登录后几轮对话内断开属于第二类，全程可用但频繁弹验证属于第三类。</p>
<h3>每个分叉配一个可执行判断</h3>
<p>「是不是出口问题」这种问法没法执行。要改成「同一配置文件换成备用出口后，症状是否复现」——能复现往环境走，不能复现往出口走。判断动作必须是一步能做完的，否则树就画不下去。</p>

<h2>二、分支 A：连登录页都进不去</h2>
<p>这一支最好查，因为失败是确定的、可复现的。</p>
<h3>先分清是「连不上」还是「连上了但被挡」</h3>
<p>连不上表现为超时、DNS 解析失败、TLS 握手报错；被挡表现为页面能开，但提交后返回错误或停在验证环节。前者是网络层，后者是业务层，处理方式完全不同。用 curl 直接请求一次，看返回码和耗时，比在浏览器里看现象准确。</p>
<h3>网络层往下分两支</h3>
<p>一支是线路本身不通：在服务商后台看在线状态，做一次连通性测试，若不通直接开工单，别自己折腾。另一支是本地出口问题：公司网络或本地代理把流量拦了，表现为只有这台机器不行、换台机器就好。这一支的处置是改本地网络策略，跟住宅 IP 没关系。</p>
<h3>业务层多半是账号或地区</h3>
<p>能打开登录页但提交失败，先核对账号状态（是否欠费、是否被要求改密），再核对出口国家与账号地区是否一致。两者不一致时，系统常会要求走额外验证流程。把出口换到与账号地区一致的那一条，再试一次。</p>

<h2>三、分支 B：能登录，但中途断</h2>
<p>这一类最磨人，因为现象随机，时好时坏。</p>
<h3>先看断的时间点有没有规律</h3>
<p>记录每次断开的时间戳，连续记三天。如果集中在某个时段，多半是带宽争抢或平台侧高峰；如果均匀分布，多半是线路抖动；如果总在长任务（解析长文档、生成长回复）时断，那是超时设置与带宽共同作用。三种规律的处置完全不同。</p>
<h3>用长任务做压测</h3>
<p>写一个脚本，连续发二十次长请求，记录每次耗时与是否完整返回。返回不完整且耗时接近某个固定值，说明是超时截断，需要调大客户端超时并降低单次请求体量；返回随机失败，说明线路不稳，该换线路。这个测试十分钟能跑完，比翻日志快。</p>
<h3>别忽略本地这一端</h3>
<p>多号同开时，本地上行带宽经常是真凶。十个浏览器窗口同时上传文件，出口再稳也扛不住。处置办法是给上传任务排队，或者把大文件拆成小块分次传。这一支跟出口质量无关，换多少条线路都没用。</p>
<h2>四、分支 C：全程可用但总被验证</h2>
<p>这一支的根因几乎都藏在「一致性」三个字里。</p>
<h3>一致性三件套</h3>
<p>出口国家、配置时区、浏览器语言，三者要指向同一个地方。常见错误是出口在美国、时区还是东八区、语言还是中文，系统一看就知道对不上。改的时候三样一起改，别只改一样。</p>
<h3>再往下是账号历史</h3>
<p>三件套都对，还是频繁验证，就要看这个号的历史：是不是刚换过地区、是不是长时间没登录、是不是曾经触发过限制。这类情况靠改配置解决不了，只能靠时间与稳定的使用节奏慢慢恢复。</p>

<h3>老号新号分开跑的意义</h3>
<p>老号历史长、包袱重，新号干净但没积累。混在同一条出口上，一旦老号出状况，新号会被牵连；反过来新号的高频操作也可能影响老号。分开跑、各自独立出口，才能让两支的问题互不传导，也让排查时能对照。</p>
<h2>五、分支 D：换市场之后才出的问题</h2>
<p>这一支往往是自找的：为了开新地区市场，把一批号整体搬到新出口，结果集体出状况，然后怀疑线路。实际原因多是切换太急、配置没跟着改、资料与地区不匹配三者叠加。处置顺序是：先把配置的地区、时区、语言全部改成目标市场，再确认出口归属与目标市场一致，最后把切换节奏放到以周为单位，一次只动一个市场。三件事按顺序做完，绝大多数集体异常会自己消退。</p>
<h2>常见问答</h2>
<h3>故障树要画多细才够用？</h3>
<p>答：三层足够。第一层分症状，第二层分归属（出口、环境、账号、本地），第三层到具体动作。再细就变成操作手册了，反而没人看。团队里贴在共享文档首页，比存在某个人脑子里有用。</p>
<h3>每次排障都要从头走一遍吗？</h3>
<p>答：不必。熟练之后可以跳步，但跳步的前提是「知道自己在跳哪一层」。新人一律从顶层走，走两三次就熟了。跳步最大的风险是把两个同时发生的问题当成一个问题。</p>
<h3>没有备用出口怎么做交叉测试？</h3>
<p>答：临时开一条按量计费的线路就够了，用几小时的成本换一个明确结论，很划算。实在不行，用同一账号在本地普通网络下试一次，也能排除掉一部分环境问题。</p>
<h3>怎么避免同样的问题反复出现？</h3>
<p>答：每次排完记一条：现象、根因、处置、复测结果。攒到二十条左右，故障树就能按自己的实际情况改写，比通用模板好用得多。</p>
<h2>合规提示</h2>
<p>本文提供的排障方法用于自有或已授权账号的日常运维，不用于探测、绕过平台安全机制或规避服务条款限制。</p>
<p>排障日志中会包含账号标识、请求内容与网络信息，应按内部规范脱敏存储并设定保留期限。</p>
